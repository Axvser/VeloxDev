# 版本管理

> 适用范围：仓库里所有包项目的版本号 —— `Src/` 下各包 csproj 的 `<Version>`。
> 本文是这一主题的唯一事实源。用户口述、agent 落笔。

## 一、格式

版本号统一写成 `x1.x2.x3`，三段都是十进制非负整数（如 `11.0.0`、`10.3.7`）。

## 二、按改动性质决定提哪一位

| 改动性质 | 结果版本 |
|---|---|
| 破坏性变更 —— 现有调用方不改代码就会编译失败或行为改变 | `{x1 + 1}.0.0` |
| 功能增量 —— 新增能力，原有用法不受影响 | `x1.{x2 + 1}.0` |
| 优化 / 修复 —— 不改契约的性能、内存、缺陷修正 | `x1.x2.{x3 + 1}` |

- **破坏性变更**：`x1` 加一，`x2` 与 `x3` 一并归零。
- **功能增量**：`x2` 加一，`x3` 归零。
- **优化 / 修复**：只加 `x3`。

## 三、判断口径

- **先判有没有破坏性，再判是不是功能增量，都不成立才是优化 / 修复。** 顺序反过来会把破坏性变更降级成次版本号。
- **一轮改动同时包含多类时，取最高的一档**：既有破坏性又有新功能，按破坏性提 `x1`；既有新功能又有修复，按功能增量提 `x2`。
- **看不准某一处改动算不算破坏性时，按破坏性处理** —— 高估只会早一个大版本，低估会让下游静默拿到不兼容的包。
- 版本号写在 18 个包 csproj 里且必须一致；发布工作流会校验这一点，不一致直接拒绝发布。

## 四、与发布的关系

`x3` 递增意味着新包替代同一 `x1.x2` 线上的旧 patch —— 发布工作流在推送成功后会 unlist 该线上所有更低的 `x3`。`x1` 或 `x2` 变化时不动旧线。
