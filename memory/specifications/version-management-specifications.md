# 版本管理

> 适用范围：仓库里所有包项目的版本号 —— `Src/` 下各包 csproj 的 `<Version>`。
> 本文是这一主题的唯一事实源。用户口述、agent 落笔。

## 一、格式

版本号统一写成 `x1.x2.x3`，三段都是十进制非负整数（如 `11.0.0`、`10.3.7`）。
版本只写在每个包自己的 csproj `<Version>` 里，不额外引入全局版本属性。

## 二、按改动性质决定提哪一位

| 改动性质 | 结果版本 |
|---|---|
| 破坏性变更 —— 现有调用方不改代码就会编译失败或行为改变 | `{x1 + 1}.0.0` |
| 功能增量 —— 新增能力，原有用法不受影响 | `x1.{x2 + 1}.0` |
| 优化 / 修复 —— 不改契约的性能、内存、缺陷修正 | `x1.x2.{x3 + 1}` |

- **破坏性变更**：`x1` 加一，`x2` 与 `x3` 一并归零。
- **功能增量**：`x2` 加一，`x3` 归零。
- **优化 / 修复**：只加 `x3`。

## 三、包的分层与跟随

| 层 | 包 | 版本规则 |
|---|---|---|
| 最底层 | `VeloxDev.Core.Generator` | 提升时必须高于全局所有包 |
| 底层 | `VeloxDev.Core` | 提升 x1 / x2 时，下游同步到它的新版本 |
| 下游 | 7 个适配器、`VeloxDev.Core.Extension`、`VeloxDev.Cli` | 可独立提升；Core 提升 x1 / x2 时同步到 Core 的新版本。**CLI 另有下限规则，见第 7 条** |
| 独立 | 7 个 `.Templates` | 不主动更新，开发者明文要求时才提 |

1. **生成器提升**：`VeloxDev.Core.Generator` 的新版本必须高于全局所有包（包括 Core）；Core 必须在同一轮提升，Core 提到 x1 或 x2 时下游按第 2 条同步。生成器不提升时，可以落后于 Core。
2. **Core 提升 x1 或 x2**：Core 的新版本必须高于所有下游当前已发布的版本（通常是在 `x2` 上领先一个、`x3` 归零）；7 个适配器、`VeloxDev.Core.Extension`、`VeloxDev.Cli` 必须同步到 Core 的新版本，并在同一轮发布。CLI 按第 7 条处理：`x1` 相等、`x2` 不低于 Core；若 CLI 的 `x2` 已经更高，保持更高，不回退到 Core 的版本。
3. **Core 只提 x3**：不强制下游跟随；下游要跟也可以，按自身改动性质提版本。
4. **下游独立提升**：Core 不动时，下游可以按自身改动性质独立提版本、独立发布。
5. **模板**：不参与上述联动。版本不变就不提、不发；只有开发者明文要求时才提版本、才发布。
6. **依赖引用**：Release 下 `PackageReference` 指向的 `VeloxDev.Core` / `VeloxDev.Core.Generator` 版本，必须与被引用包 csproj 里的 `<Version>` 一致。下游同步到 Core 新版本时，这些引用一起改。
7. **CLI 的版本锚定 Core**：`VeloxDev.Cli` 的 `x1` 必须与 `VeloxDev.Core` 的 `x1` 相同；`x2` 必须 **≥** Core 的 `x2`；`x3` 必须 ≥ Core 的 `x3`，且 ≥ `VeloxDev.Core.Extension` 的 `x3`。CLI 同时承载两者，主版本不能跑到 Core 前面、次版本与补丁号都不能低于被承载包；CLI 可以独立提 `x2`，但 Core 不能反过来落后到 CLI 的 `x2` 之上。**发布工作流只检查每个包自己的版本是否已在 NuGet，不替这条规则做门禁**；版本关系由开发过程中维护。

## 四、判断口径

- **先判有没有破坏性，再判是不是功能增量，都不成立才是优化 / 修复。** 顺序反过来会把破坏性变更降级成次版本号。
- **一轮改动同时包含多类时，取最高的一档**：既有破坏性又有新功能，按破坏性提 `x1`；既有新功能又有修复，按功能增量提 `x2`。
- **看不准某一处改动算不算破坏性时，按破坏性处理** —— 高估只会早一个大版本，低估会让下游静默拿到不兼容的包。
- **先判层，再判位**：Core 或生成器提升时，先按 §三 确定哪些包必须跟随，再对每个包按 §二 判断它自己的改动该提哪一位。
- **CLI 先看 Core 与 Extension**：给 CLI 定版本时，`x1` 必须等于 Core 的 `x1`；`x2` 以 Core 的 `x2` 为**下限**（可以更高）；`x3` 以 `max(Core.x3, Extension.x3)` 为下限。不满足就不要发包；当前版本不满足时，先把它修到满足，再谈补丁号。
- **模板不活跃**：不因为 Core 或下游提升就顺手改模板版本；没有明文要求就不动。

## 五、与发布的关系

- 发布工作流按**每个包自己的 `<Version>`** 判断是否已发布；已在 NuGet 上的包跳过，只发缺的。
- 发布顺序：`VeloxDev.Core.Generator` → `VeloxDev.Core` → 下游与模板。下游 nuspec 里的 Core 依赖由该包 csproj 的 `PackageReference` 决定，打包前先按 §三.6 对齐。
- `x3` 递增时，发布工作流 unlist **该包自己** `x1.x2` 线上更低的 patch；`x1` / `x2` 变化不动旧线。没有在本次发布的包不会被清理。
- 模板不随 Core 发布；版本不变就不会发布。

## 六、版本号提交

- **版本号变更必须单独成提交**：只放 csproj 的 `<Version>` 变更，以及按 §三.6 必须同步修改的依赖引用版本；不要和代码、测试、模板、文档改动混在同一笔。代码改动先按自己的 `[类型][模块]` 提交，最后再用一笔 `[config][repo]` 提交版本号。
- 同一轮多个包同步提升时，放在**同一笔版本提交**里，在表格中逐行列出；不要一个包一笔。
- **提交信息必须列出四个维度**，缺任何一列都不合规：

  | 包名 | 原版本 | 提升后的版本 | 修改简述 |
  |---|---|---|---|
  | `VeloxDev.Core` | 11.0.0 | 11.1.0 | 新增布局批次公共 API，功能增量 |
  | `VeloxDev.WPF` | 11.0.0 | 11.1.0 | 跟随 Core 的 x2 提升 |

  四列的含义：
  - **包名**：csproj 的 PackageId / 项目名；
  - **原版本**：改动前的 `<Version>`；
  - **提升后的版本**：改动后的 `<Version>`；
  - **修改简述**：为什么提这一位（破坏性 / 功能增量 / 优化修复），一句话。

- 版本号提交的 body 仍按 [commit-message-specifications.md](commit-message-specifications.md) 的 `[what]` / `[why]` / `[how]` 写；上表放在 `[what]` 下。首行示例：`[config][repo] the packages move to 11.1.0`。

**自查（提交版本号之前）**：

- [ ] 这一笔是否只包含 `<Version>` 与按 §三.6 必须同步的依赖引用版本？
- [ ] 四列表（包名 / 原版本 / 提升后的版本 / 修改简述）是否齐全，每行一个包？
- [ ] 首行是否是 `[config][repo] ...`，且没有把代码/测试/文档混进来？
