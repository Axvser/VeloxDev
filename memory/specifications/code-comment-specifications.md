# 代码注释风格

> 适用范围：`Src/` 下所有手写源码 —— `.cs` 的成员注释与函数体注释，以及 `.xaml` / `.axaml` / `.razor` 的标记注释。
> 本文是这一主题的唯一事实源。

全文只有一条分界线：**这个成员在仓库外能不能被访问到。** 能，走第一节；不能，走第二节。

---

## 一、公开可访问的成员

**判据**：`public` 与 `protected`（含 `protected internal`）成员，以及它们所属的类型。适配器里实现 Core 接口的成员同样算 —— 它们由外部调用。

三条硬性要求，缺一不可：

1. **必须用 XML 注释**（`///`）。这是 `GenerateDocumentationFile` 产出的文档文件里消费者读到的内容。
2. **必须用英语。**
3. **必须说清职责** —— 它负责什么，而不是它内部怎么做的。

### 优先用带高亮的标签

`<summary>` 里裸写类型名、参数名、关键字，读者拿到的是死文本；用标签包起来，IDE 才会高亮、才能跳转。**默认用标签，而不是默认写纯文本。**

| 要引用的东西 | 标签 |
|---|---|
| 类型、成员、重载 | `<see cref="X"/>`；重载带签名，如 `<see cref="Seek{T}(T, TimeSpan, bool, bool)"/>` |
| 类型参数 | `<typeparamref name="T"/>` |
| 参数 | `<paramref name="target"/>` |
| 行内代码、关键字、字面值 | `<c>Task.Run</c>` |
| 多行代码 | `<code>` |
| 会抛出的异常 | `<exception cref="ArgumentOutOfRangeException">` 并写明触发条件 |
| 「另见」 | `<seealso cref="X"/>`，挂在正文末尾 |

`<seealso>` 与 `<see cref>` 的分工：**正文里提到**就用 `<see cref>`；**正文讲完了，还想主动指一条「你接下来该看这里」的路**，才用 `<seealso>`。不必每个公开成员都挂 `<seealso>` —— 只在确实存在一个自然的下一站时挂。关联类、配套方法、该先读的东西，都归它。

### 长理由放 `<remarks>`

`<summary>` 一句话说清职责，短到一行时可以直接写在一行里。
要展开的是**契约** —— 时序、线程、边界、以及「为什么这样设计会影响调用方」，放 `<remarks>`，分段用 `<para>`。

不要把实现细节写进 `<remarks>`：那是函数体注释的活（见第二节），而且这里的读者是调用方，不是维护者。

### override 用 `<inheritdoc />`

重写成员、实现接口成员继承基成员的文档，不复制正文。这是本仓库的既有惯例。

### 边界

- 编译器**不**强制这一节：`CS1591` 在 Core、WPF、Jalium 中已被 `NoWarn` 关掉，其余项目根本不生成文档文件。漏写注释不会构建失败，约束力全部来自本文。
- 旧文件里，`internal` / `private` 成员上仍留着英语 `///`（那是本节之前的写法）。**不要为此整仓重写**；改到哪一行，就把那一行按本文回归。

## 二、非公开成员

**判据**：`internal`、`private`，以及函数体内部的局部说明。

- **用 `//`** —— 单行，或连续多行 `//`。**不用 `///`**：那只会污染文档文件。
- **必须用简洁的简体中文。** 写完回头删掉一半仍然成立，就是对的长度。

### 什么时候必须写

**成员注释**：命名不具备普遍性时必须写。名字本身讲不清它是什么、为什么存在、边界在哪 —— 补一行。名字很鲜明时可以省略。

**函数体**：关键部分必须写。判据是「一个熟悉本项目的人扫过去，会不会在这里停一下」。典型触发点：

- 平台硬限制与反直觉行为；
- 时序假设，以及它被破坏时的后果；
- 看着可以简化、但不能简化的地方；
- 某个常量为什么是这个值；
- 刻意背离通则之处。

### 不写

- 复述代码的字面意思。
- 教科书式的通用解释。
- **已经不成立的旧注释，比没有注释更糟** —— 改代码时同步改它。

---

## 三、理由写在哪里

注释只留**结论**：结论是事实，事实属于读代码的人。

推导过程、失败过的方案、量到的数字，写在 commit message 里 —— 那是想看长文的人该去的地方，而不是每个读到这一行的人都要付的成本。提交信息怎么写见 [commit-message-specifications.md](commit-message-specifications.md)（首行 `[类型][模块]`，body 三段 `[what]` / `[why]` / `[how]`）。

## 四、标记注释（`.xaml` / `.axaml` / `.razor`）

**判据**：这些文件里的注释。

要求与第一节的公开成员**同一条线**，而不是第二节那条：

- **必须用英语。**
- **简洁** —— 写完回头删掉一半仍然成立，就是对的长度；能一行说清就一行。
- 只留**结论**，推导过程与量到的数字仍归 commit message（见第三节）。

理由与第二节相同：这里的读者不需要为一行注释付长文的成本，而标记语言的读者与 `.cs` 的读者是同一批人 —— 两种语言写同一件事只会让其中一份先腐坏。

---

## 五、模板注释（`Src/Templates/*/working/content/`）

**模板注释只解释扩展点，永远不解释机制、原理。**

- 该写的是「这里可以改什么、改的时候要跟什么保持一致」—— 使用者拿到模板后要动手的地方；
- 机制、原理、为什么这样设计：写进模块记忆（`memory/modules/`）或提交信息，**不写进模板**。

§一 与 §四 的英语要求同样适用于模板；本节是对**内容**的额外限制 —— 语言对了不等于内容对了。

## 六、自查

提交前，对照你动过的每一行，问五个问题：

1. 这一行在仓库外能被访问到吗？是 → 英语 `///`；否 → 简体中文 `//`。
2. 这一行里提到的类型、参数、关键字，都带标签了吗？
3. 这一行说的是「它负责什么」，还是「它内部怎么做的」？后者留在函数体里。
4. 是 `.xaml` / `.axaml` / `.razor` 的标记注释吗？是 → 英语、简洁（见第四节）。
5. 在 `Src/Templates/*/working/content/` 里吗？在 → 这条注释只说扩展点，不说机制（见第五节）。
