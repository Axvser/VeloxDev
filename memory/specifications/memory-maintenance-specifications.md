# 模块记忆维护

> 适用范围：[`memory/modules/`](../modules/) 下的一切。**由 agent 自主维护** —— 不需要用户开口。
> 本文是这一主题的唯一事实源。

**与 [`memory/specifications/`](.) 的分工**：`specifications/` 下的规范手册由用户口述、agent 落笔，效力来自用户认可 —— agent **不自行新增或改动**它们。模块记忆相反：agent 是它的唯一作者与责任人。自己定的规范没有约束力，自己写的记忆才有。

---

## 一、目录

```
memory/
├─ specifications/             # 规范手册,agent 只读
└─ modules/
    └─ <模块名>/
        ├─ architecture.md     # 必备
        ├─ extension.md        # 必备
        ├─ <主题>.md            # 其余细节、踩坑
        └─ adapters/           # 模块存在平台差异轴时才有,见第四节
            └─ <平台>.md
```

**模块名**：原样沿用 `Src/` 里的目录名或项目名 —— `TransitionSystem`、`WorkflowSystem`、`VeloxDev.WPF`、`VeloxDev.Core.Generator`。这样「模块名 → 代码在哪」是零成本的，不需要任何映射表。

**粒度**：以 `Src/Core/VeloxDev.Core/<主题>/` 这一级为准；七家适配器各算一个模块。**不要按文件建模块** —— 那会退化成第二份文件清单。

**不建模块索引**：找模块直接 `ls memory/modules/`。索引文件只会多一处会过期的地方。

---

## 二、两份必备

一个功能模块**至少**要有这两份。它们服务两个不同的问题，不能合并。

### `architecture.md` —— 服务于「快速理解代码」

它存在的唯一理由是**省掉通读代码的成本**。所以它必须是一份**提炼**，不是**副本**。

类型清单、成员列表、继承树，IDE 里一按就有 —— **凡是读一眼代码就知道的，不写。** 写了只会让它和代码一起腐坏，而且没人会因为省了这一眼而感谢你。

要写的是**读完之后才知道的东西**：

- 这个模块解决什么问题，**不解决**什么；
- 核心类型各自的**职责边界** —— 谁拥有状态，谁只是搬运，谁是唯一写者；
- 数据/控制流向 —— 从哪个入口进，经过谁，从哪出来；
- **不变量** —— 什么必须在什么之前、什么必须成对出现、违反了会怎样；
- 分层与依赖方向 —— 谁能引用谁，反向为什么不行；
- 入口 —— 我要改某个行为，先打开哪个文件。

**判据**：agent 读完能回答「我要改的这个行为，归哪个类型管」。

### `extension.md` —— 服务于「怎么走正确的路」

这份更容易写废：它必须**可执行**，不能只是把扩展点罗列一遍。

- **扩展点在哪** —— 接口、虚方法、特性、注册表、约定命名，逐个说到具体成员；
- **官方做法 vs 看着能编译、但错的捷径**。这条最重要 —— 本仓库几乎每个扩展点都能用错误的方式绕过，而且照样编译通过、甚至跑起来像是好的；
- **新增一个 X 的步骤清单** —— 按顺序，每步写清「改哪个文件、加什么」；
- **联动清单** —— 加一个 X 时**必须同步修改的所有位置**：枚举、`switch`、生成器、七家适配器、模板。**这是本仓库最容易漏的地方**：漏一处通常不报错，而是静默少一个能力，等到用户那边才发现。

**判据**：agent 读完能回答「要加一个新 X，我该动哪几处，按什么顺序」。

## 三、其余细节文件

按**主题**命名，不按时间命名 —— 写 `pitfalls.md`，不写 `2026-09-05-xxx.md`（时间名对下一个读者没有任何信息量）。典型主题：

- `pitfalls.md` —— 实测踩过的坑：平台陷阱、反直觉行为、失败过的方案及其原因；
- 具体子系统 —— 如 `virtualization.md`、`serialization.md`、`zoom.md`。

**写坑必须带依据，而依据只能在树里**：写 `文件:行`（或一个能直接定位过去的符号名）。**不要拿 commit / PR / 提交信息当依据** —— 读记忆的 agent 手上只有工作区，核不到的东西等于没写；提交信息记的是**当时的意图**，代码才是**当下的事实**，两者不一致时以代码为准，而这时 commit 反而会把人带偏。**量到的数字要保留**（px、帧数、耗时、阈值）—— 它们是以后判断「这条还算不算数」的锚点，删掉数字这条记忆就只剩一句无法验证的感受；数字若只存于提交历史、代码里复核不到，就**标明它不可复核**而不是删掉数字。

## 四、平台差异：`adapters/` 子目录

**什么时候加**：模块的核心代码定义一份契约、各平台各自实现一份 —— 也就是本仓库的 Adapter 模式。当前有两个模块存在这条轴：[`TransitionSystem`](../modules/TransitionSystem/)、[`WorkflowSystem`](../modules/WorkflowSystem/)。

**为什么必须单独成篇**：平台差异是**共性之外的例外**，混进 `architecture.md` 会把共性淹掉 —— 而 `architecture.md` 的价值恰恰是「不用读七份实现就能理解这个模块」。每多一家平台就多一份差异，所以它得有自己的位置。

```
<模块名>/
└─ adapters/
    ├─ wpf.md
    ├─ avalonia.md
    ├─ winui.md
    ├─ maui.md
    ├─ winforms.md
    ├─ razor.md
    └─ jalium.md
```

**文件名**：小写平台名，对齐 [`skills/veloxdev-create-workflow/references/gui/`](..\..\skills\veloxdev-create-workflow\references\gui\) 的既有命名。**一家平台一份，不管这家多简单** —— 缺文件与「这家没有差异」是两件事，前者让下一个 agent 以为没人写过。

**契约本身不进 `adapters/`**：所有平台共同的部分（要实现的接口、注册方式、生命周期钩子）写在模块的 `extension.md` 里，在 `adapters/` 里重复七遍是浪费且必然走样。

**一份平台文件写四件事**：

1. 这家**必须实现契约的哪些成员**，以及为什么是这些；
2. 这家的**平台硬限制**，与由此产生的做法 —— 这是全篇最有价值的部分，因为它决定了别家能照抄什么；
3. 与其它家的**刻意背离**及理由（此处必须有明确的肯定句，「这里的做法和其他家不一样，因为…」）；
4. 改这里时最容易踩的坑，按第三节的要求带依据。

**判据**：一个要新接一家平台的人读完，知道自己要写什么、哪里不能照抄别家。

## 五、什么时候写、什么时候改

**落笔前先摸清这个模块的既有写法。** 跑一次 `git log --oneline -- <模块路径>` 看最近的提交怎么做、牵动了哪些文件、踩过哪些雷 —— 记忆的**粒度与风格**照它校准，而不是自己现发明一套。提交信息里已经带了 `[what]` / `[why]` / `[how]` 三段（见 [commit-message-specifications.md](commit-message-specifications.md)），推导、失败过的方案、量到的数字都在那儿；记忆要写的是它们**装不下**的东西 —— 当下的代码事实、扩展时要走的路、半年后仍然成立的坑。

**写**：任务完成后，若你产生了「下一个 agent 不知道就会重新踩一遍」的知识，就写进对应模块。这是本职，不是额外工作。

**改**：

- 已有记忆与你的新发现冲突 → **改那一句**，不要在下面追加一段矛盾的文字。两份互相矛盾的记忆比没有记忆更糟 —— 下一个 agent 会随机信一份。
- 记忆为真，是**写它的时候**为真。按记忆里提到的文件名 / 方法名去核代码；核不到，说明它过期了 —— 改掉或删掉。

**不写**：

- 代码结构一眼能看出的（见第二节）；
- 只在本次对话里成立的；
- 长文推导 —— 提交信息里已经有了（三段 `[what]` / `[why]` / `[how]`，见 [commit-message-specifications.md](commit-message-specifications.md)），再抄进记忆只是第二份会过期的副本。记忆只留**结论 + 代码锚点 + 数字**。

## 六、自查

1. 动过的模块，`architecture.md` 和 `extension.md` 都在吗？
2. `architecture.md` 里有没有「读一眼代码就知道」的内容？有就删。
3. `extension.md` 里写了「官方做法 vs 错的捷径」吗？只有扩展点清单是不够的。
4. 模块有平台差异轴吗？有的话 `adapters/` 下七家的文件齐吗（缺文件 ≠ 无差异）？契约有没有被重复七遍？
5. 新写的坑点带依据了吗？依据必须是树里的 `文件:行`（或可定位的符号名）—— **不是 commit**。数字留了吗？复核不到的数字标出来了吗？
6. 动过的旧记忆，你是**改**了它，还是在下面追加了一段？
